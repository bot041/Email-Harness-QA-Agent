1. PROJECT OVERVIEW
================================================================================

The Email Harness QA Agent is a web application that reviews already-written
emails and generates a professional QA report BEFORE the email is sent.

It does NOT generate or rewrite emails. Instead, it acts as a quality
gate — identifying issues, explaining why they matter, and providing
actionable recommendations.

Think of it as a "spell-check + proofreader + communication coach" for
professional emails, powered by a hybrid approach of deterministic rules
AND AI semantic analysis.

Core Promise: Paste an email → Get a QA report → Fix issues → Send with
confidence.

================================================================================
2. PROBLEM STATEMENT
================================================================================

Professionals send dozens of emails daily, and small mistakes can have
outsized consequences:
  - A missing subject line → email gets ignored or marked as spam
  - A typo → undermines credibility with clients or executives
  - An unclear call-to-action → delays and miscommunication
  - An overly casual tone → damages professional relationships

Existing solutions (Grammarly, etc.) focus on grammar alone. They don't
understand email-specific concerns like subject quality, greeting
appropriateness, CTA clarity, or duplicate content.

This agent solves that by combining:
  - FAST deterministic rules (instant checks for structural issues)
  - DEEP AI analysis (semantic review of tone, clarity, professionalism)

3. ARCHITECTURE & DESIGN PHILOSOPHY
================================================================================

The project follows a SINGLE AGENT architecture — one orchestrator that
manages the entire pipeline. This is deliberate:

  ✅ Simpler to understand, debug, and extend
  ✅ No inter-agent communication overhead
  ✅ Deterministic flow: parse → validate → review → report
  ✅ Easy to add new validators (just register in the rule engine)

The HYBRID approach is key to the design:

  ┌─────────────────────────────────────────────────────┐
  │                 Email Harness Agent                   │
  │                 (Orchestrator)                        │
  │                                                       │
  │  1. Parse Email ──→ Structured Fields                 │
  │  2. Run Rule Engine ──→ Deterministic Issues          │
  │  3. Run DeepSeek AI ──→ Semantic Issues               │
  │  4. Filter False Positives ──→ Clean Issues           │
  │  5. Determine Status ──→ Ready / Needs / Not Ready    │
  │  6. Build QA Report ──→ Unified Output                │
  └─────────────────────────────────────────────────────┘

Why NOT send everything to the AI?
  → LLMs are slow and expensive for simple checks.
     "Is the subject empty?" doesn't need AI — a regex is faster,
     cheaper, and 100% reliable.

Why NOT use only deterministic rules?
  → Rules can't judge tone, clarity, or professionalism. You need
     semantic understanding for that.

    microservice. No ORM needed (no database).

Why DeepSeek?
  → Cost-effective compared to GPT-4, strong performance on structured
    JSON output tasks, and the chat completions API is OpenAI-compatible
    making it easy to swap later.

6.1 EMAIL PARSER (app/utils/email_parser.py)
────────────────────────────────────────────

Purpose: Convert raw pasted email text into structured fields.

Input:  Raw text (copied from Gmail, Outlook, or typed)
Output: Dict with: sender, recipients[], date, subject, greeting,
        body, closing, signature

How it works:
  Step 1 — Header Detection (lines 37-78):
    Scans for "From:", "To:", "Cc:", "Date:", "Subject:" patterns
    using regex. Extracts structured data from each header line.
    Stops when it hits body-like content (e.g., "Dear...", "Hi...").

  Step 2 — Greeting Extraction (lines 91-102):
    Matches common greeting patterns:
      "Dear [Name],"
      "Hi [Name],"
      "Hello [Name],"
      "Good morning/afternoon/evening [Name],"
    Preserves the comma if present (critical for accuracy).

  Step 3 — Closing Detection (lines 104-129):
    Matches common closings:
      "Best regards", "Sincerely", "Thanks", "Cheers",
      "Kind regards", "Warm regards", etc.

  Step 4 — Signature Extraction (lines 131-137):
    Everything after the closing is treated as signature.

  Step 5 — Email Address Extraction (lines 155-171):
    Uses email regex to pull addresses from "Name <email>" format.
    Deduplicates recipients while preserving order.

Key Design Choice: No AI needed for parsing. Regex is deterministic,
fast, and handles 95%+ of real-world email formats.

6.2 RULE ENGINE VALIDATORS (app/validators/rule_engine.py)
───────────────────────────────────────────────────────────

Purpose: Fast, deterministic checks — no AI calls.

The rule engine runs 4 validators. Each validator returns a
ValidationResult with: validator_name, passed (bool), issues (list).

┌──────────────────────────────────────────────────────────────┐
│ VALIDATOR 1: SubjectValidator                                 │
├──────────────────────────────────────────────────────────────┤
│ Checks:                                                       │
│  ✅ Subject exists                                            │
│  ✅ Subject length (3-100 chars is reasonable)                │
│  ✅ Subject is not generic ("Meeting", "Hello", "Update",     │
│     "Urgent", "FYI", etc. — 17 common generic words)         │
│  ✅ Subject is not ALL CAPS (looks aggressive/spam-like)      │
│                                                               │
│ Why it matters: Subjects determine whether your email gets     │
│ opened. Generic or missing subjects reduce response rates.    │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ VALIDATOR 2: RecipientValidator                               │
├──────────────────────────────────────────────────────────────┤
│ Checks:                                                       │
│  ✅ At least one recipient exists                             │
│  ✅ Recipient email format is valid (regex validation)        │
│  ✅ No duplicate recipients (case-insensitive dedup)          │
│  ✅ Not too many direct recipients (>10 warns about BCC)      │
│                                                               │
│ Why it matters: Invalid recipients cause bounces. Duplicates  │
│ annoy people. Exposing many addresses violates privacy.       │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ VALIDATOR 3: GreetingValidator                                │
├──────────────────────────────────────────────────────────────┤
│ Checks:                                                       │
│  ✅ Greeting exists (or body starts with greeting-like word)  │
│  ✅ Greeting is not overly casual ("Yo", "Sup", "Wassup",     │
│     "Oi", "Heya")                                             │
│  ✅ Greeting is personalized (not generic "Hi there",         │
│     "Dear Sir/Madam", "To Whom It May Concern", etc.)         │
│                                                               │
│ Why it matters: Greetings set the tone. Missing or overly     │
│ casual greetings feel abrupt. Generic greetings feel          │
│ impersonal. Personalized greetings build rapport.             │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ VALIDATOR 4: DuplicateContentDetector                         │
├──────────────────────────────────────────────────────────────┤
│ Checks:                                                       │
│  ✅ No repeated paragraphs (>30 chars, normalized comparison) │
│  ✅ No repeated sentences (>20 chars, normalized comparison)  │
│                                                               │
│ Why it matters: Repeated content suggests the email wasn't    │
│ proofread. It wastes the reader's time and buries the key     │
│ message.                                                      │
└──────────────────────────────────────────────────────────────┘

Each validator is independent — you can add, remove, or modify them
without touching any other code. New validators just need to:
  1. Implement validate(parsed_email) → ValidationResult
  2. Register in run_rule_engine()

6.3 DEEPSEEK AI SERVICE (app/services/deepseek_service.py)
───────────────────────────────────────────────────────────

Purpose: Semantic email review for issues that rules can't catch.

What it evaluates:
  1. Grammar — tense issues, subject-verb agreement
  2. Spelling — typos, misspellings
  3. Clarity — confusing sentences, ambiguous phrasing
  4. Professionalism — appropriate tone for business context
  5. Call-to-Action (CTA) — does the recipient know what to do?
  6. Tone — respectful, appropriate, not aggressive
  7. Overall — is this email ready to send?

How it works:
  Step 1 — Format the parsed email into a review text block
  Step 2 — Build a structured prompt with clear instructions
  Step 3 — Send to DeepSeek API (temperature=0.3 for consistency)
  Step 4 — Parse the JSON response (handles code fences if present)
  Step 5 — Return structured dict: {issues, summary, overall_assessment}

Fallback Mode:
  If no API key is configured (or key starts with "sk-your-"),
  the service falls back to _mock_review() — heuristic checks for:
    - Empty body (critical)
    - Very short body (<10 words)
    - Very long body (>2000 words)
    - Common typos ("recieve"→"receive", "definately"→"definitely", etc.)
    - Excessive punctuation (!!!, ???)
    - Missing call-to-action
  This makes the app fully functional even without an API key.

Prompt Engineering Details:
  - System message: "Expert email QA reviewer" role
  - Structured output: Forced JSON format with specific schema
  - Temperature 0.3: Balances consistency with some flexibility
  - Max tokens 2000: Enough for detailed issues + summary
  - Timeout 30s: Prevents hanging on API issues

6.4 EMAIL HARNESS AGENT (app/agents/email_harness.py)
──────────────────────────────────────────────────────

Purpose: The central orchestrator. This is the "brain" of the system.

Class: EmailHarnessAgent
  - __init__(): Sets the goal to "Review this email."
  - review(raw_email_text) → QAReport: The main pipeline
  - _filter_harness_false_positives(issues) → (filtered, count)
  - _determine_overall_status(...) → status string
  - _build_final_recommendation(...) → recommendation string

The review() pipeline (8 steps):

  Step 1: Parse the email into structured fields
  Step 2: Run all 4 rule engine validators
  Step 3: Run DeepSeek semantic review
  Step 4: Aggregate all issues from both sources
  Step 5: Filter out Harness template expression false positives
  Step 5b: If ALL DeepSeek issues were false positives, treat
           assessment as "Ready to Send" (prevents contradictory
           "0 issues but Not Ready to Send" state)
  Step 6: Determine overall status
  Step 7: Build validation summary with counts
  Step 8: Build final recommendation and return QAReport

Status Determination Logic:
  - "Not Ready to Send": Blocking issues from rule engine (missing
    subject, no recipient, empty body) OR DeepSeek says Not Ready
  - "Needs Review": 1+ issues found but no blockers
  - "Ready to Send": Zero issues

6.5 DATA MODELS (app/validators/models.py)
───────────────────────────────────────────

@dataclass Issue:
  title: str            # "Missing Subject Line"
  description: str      # "The email has no subject line."
  why_it_matters: str   # "Emails without subjects are often ignored..."
  recommendation: str   # "Add a concise, descriptive subject..."
  source: str           # "rule_engine" or "deepseek"

@dataclass ValidationResult:
  validator_name: str   # "Subject Validator"
  passed: bool          # True if no issues found
  issues: list[Issue]   # List of issues (empty if passed)

@dataclass QAReport:
  overall_status: str          # "Ready to Send" | "Needs Review" |
                               # "Not Ready to Send"
  validation_summary: dict     # {total_checks, passed, issues_found,
                               #  rule_engine_results, deepseek_assessment}
  issues: list[Issue]          # All issues found
  ai_review_summary: str       # 2-4 sentence AI summary
  final_recommendation: str    # Actionable final guidance

Design Choice: Using Python dataclasses gives us type safety without
the overhead of Pydantic or SQLAlchemy (no database needed).

================================================================================

1. User opens the web app (http://127.0.0.1:5000)
2. User pastes a complete email into the text area
   (or clicks "Load Sample" to try a pre-built example)

   - List of issues with explanations and fixes
   - AI review summary
   - Final recommendation
6. User reads issues, fixes their email, pastes again
7. Process repeats until "Ready to Send"

9. KEY DESIGN DECISIONS & TRADE-OFFS
================================================================================

Decision 1: Single Agent, NOT Multi-Agent
  Why: The problem space (review one email) doesn't benefit from
       multiple agents. A single orchestrator is simpler, faster,
       and easier to debug.
  Trade-off: Less parallelization, but email review is fast enough
       that it doesn't matter (< 5 seconds total).

Decision 2: Hybrid Rule Engine + AI, NOT AI-only
  Why: Rules are instant and deterministic. AI is slow and can
       hallucinate. Use rules for structural checks, AI for
       semantic understanding.
  Trade-off: Two code paths to maintain, but each is simple.

Decision 3: Vanilla JavaScript, NOT React/Vue
  Why: The UI is a single page with one interactive flow. No need
       for component state management or virtual DOM.
  Trade-off: Would be harder to scale to a complex SPA, but that's
       not the goal.

Decision 4: Regex Parser, NOT ML/NLP Parser
  Why: Email headers follow predictable patterns. Regex is fast,
       deterministic, and handles 95%+ of cases.
  Trade-off: Edge cases like non-standard headers might be missed,
       but they're rare in practice.

Decision 5: No Database, No Authentication
  Why: This is a tool, not a platform. Each review is independent.
       No need to store data.
  Trade-off: No history, no multi-user support. Acceptable for MVP.

Decision 6: DeepSeek over GPT-4
  Why: 10-20x cheaper, comparable quality on structured tasks,
       OpenAI-compatible API for easy migration.
  Trade-off: Slightly less nuanced on very complex emails, but
       more than sufficient for professional email review.

10. GUARDRAILS & FALSE-POSITIVE PREVENTION
================================================================================

The system uses a DEFENSE-IN-DEPTH strategy to prevent false positives:

LAYER 1 — Prompt Engineering (deepseek_service.py):
  The DeepSeek prompt explicitly instructs the model to ignore:
  ✅ Harness CI/CD template expressions (<+pipeline.name>,
     <+pipeline.executionId>, etc.) — valid runtime variables
  ✅ Minor signature formatting (spacing around colons, emoji vs
     text labels, inconsistent contact detail styles)
  ✅ The prompt tells the model to focus on what matters: grammar,
     spelling, clarity, tone, CTA, and missing critical elements

LAYER 2 — Post-Processing Filter (email_harness.py):
  After collecting all issues, the agent runs a filter that removes
  any issue where the title or description:
  ✅ Contains <+...> pattern (Harness template expression syntax)
  ✅ Contains keywords: "placeholder", "unresolved", "template
     expression", "harness", "not resolved"

LAYER 3 — Effective Assessment (email_harness.py):
  If ALL DeepSeek issues were false positives and got filtered out,
  the assessment is promoted to "Ready to Send" instead of showing
  a contradictory "0 issues but Not Ready to Send".

LAYER 4 — Greeting Comma Preservation (email_parser.py):
  The parser preserves the original comma in greetings. "Dear
  Hiring Team," stays as "Dear Hiring Team," — preventing false
  "missing comma" flags from the AI.
